\begin{abstract}
% ============================================================
Large language models (LLMs) are increasingly used as natural-language interfaces for probabilistic reasoning, but end-to-end evaluations often conflate failures of parsing, probabilistic computation, and decision-making.
We make two contributions.
First, we introduce Parse--Compute--Decide (PCD), a gold-intervention diagnostic that isolates these stages by supplying gold structure or gold posteriors.
Across six LLMs and several probabilistic tasks, models usually recover task structure and choose correct actions from a posterior, but remain unreliable probabilistic calculators: compute-stage accuracy ranges from 28\% to 78\% on preference learning and drops to 3--11\% on depth-10 Bayesian networks.
Second, we propose Verified Solver Induction (VSI), a compile-once, reuse-many framework for reliable LLM-assisted probabilistic reasoning.
Unlike direct prompting or per-instance PAL, VSI changes the role of the LLM from a per-instance calculator or code generator into a task-family-level solver inducer: an off-the-shelf LLM assembles a reusable typed solver specification from probabilistic atoms and inference routes.
A deterministic compiler lowers the specification into an executable solver for finite discrete models, runs acceptance checks and compares against references when available, and caches accepted solvers for future same-family instances.
At run time, exact inference is performed by the compiled solver rather than the LLM.
We evaluate VSI on preference learning, bandits, Bayesian networks, Naive Bayes, and HMM filtering.
VSI matches reference solvers on 1,150 Flight/BLInD instances and 400 finite-query bnlearn checks.
On external QUITE queries, VSI reaches 96.0\%, compared with 36.0--60.0\% for direct answering and 24.0--88.0\% for per-instance PAL.
On natural-language Naive Bayes and HMM tasks, VSI reaches 90.8\% and 97.6\%, while direct LLM computation reaches only 18.2\% and 32.4\% even from structured inputs.
Together, PCD identifies probabilistic computation as the bottleneck, and VSI turns LLMs from brittle probabilistic calculators into compile-time inducers of solver-backed probabilistic interfaces without fine-tuning.
\end{abstract}

\section{Introduction}
\label{sec:intro}
% ============================================================

Ask a frontier LLM to solve a ten-node Bayesian network by variable elimination and it answers correctly only 11\% of the time.
Ask the same model to identify the variables, conditional probability tables, evidence, and query, and it succeeds on nearly all instances~\citep{nafar2025blind}.
This is the failure mode we study: the model often understands the problem but cannot reliably execute the probabilistic computation.

\begin{figure*}[t]
\centering
\includegraphics[width=\textwidth]{figures/figure1_overview_4k_h092.png}
\caption{Compile-once architecture with router-mediated reuse. Mixed natural-language inputs first pass through a scope/family router, which either rejects unsupported tasks or routes supported families to induction and reuse. When no solver is available, an LLM inductor assembles a declarative \taskspec{} from typed probabilistic building blocks; a deterministic compiler lowers it to typed operations or core-op-backed routes, and a two-gate deploy check validates primary-family solvers when held-out labels are available. Validated LLM-assembled solvers are stored in a reusable registry so later same-family instances can bypass LLM induction and execute deterministically. Backend exactness is conditional on a valid \taskspec{}; natural-language E2E and router metrics are reported separately.}
\label{fig:overview}
\end{figure*}

The usual fixes do not quite address this abstraction gap.
Chain-of-thought~\citep{wei2022cot} leaves the model doing the math.
Program-aided prompting asks the model to write new code for each instance.
Bayesian Teaching, introduced on the Flight/Hotel preference tasks~\citep{qiu2026bayesian}, takes a training-side route: fine-tune a model to follow Bayesian demonstrations.
Family-specific tools such as ProbLog for Bayesian networks~\citep{nafar2025blind,deraedt2007problog} solve one benchmark family at a time.
A per-instance parser-to-library pipeline is safer than free-form code, but it still treats each input as a fresh extraction problem.
Our question is different: can an off-the-shelf LLM, with no weight updates, write a reusable solver by composing typed probabilistic atoms, pass a deploy check once, and then reuse the compiled solver across future instances?

We first show why this is the right split.
Parse--Compute--Decide (PCD) isolates three stages by injecting gold intermediate results: Parse tests structure extraction; Compute$\mid$GoldParse tests numerical inference given perfect structure; Decide$\mid$GoldPosterior tests the final action given the correct posterior.
Across six models, Parse is usually high and Decide is essentially solved, but Compute remains poor: 28--78\% on preference learning and only 3--11\% at depth~10 on BLInD Bayesian networks.
The problem is not simply that the model cannot read the task; it is that probabilistic inference is the wrong thing to leave inside the language model.

We therefore build the LLM-facing interface as a compiler target rather than a prompt.
We call this approach Verified Solver Induction (VSI).
The LLM writes a declarative \taskspec{} for a task family, effectively assembling a solver from typed probabilistic building blocks.
A deterministic compiler lowers that specification to a small typed probabilistic DSL, validates the resulting solver against held-out labels when available, and stores it for reuse (Figure~\ref{fig:overview}).
Later instances from the same family can be parsed and solved without asking the LLM to perform inference.

This design gives a clean separation between backend correctness, language-interface robustness, and routing composition.
Given LLM-assembled specifications that pass the deploy check, the compiled solvers match references on Flight/BLInD and finite-query bnlearn checks, including standard multi-valued bnlearn networks where per-instance generated code is unreliable.
On QUITE, a separate external Bayesian-inference corpus, the registered path reaches 96.0\% on the same 75-query split, compared with 60.0\% for direct GPT-5.4 and 88.0\% for PAL with GPT-5.4.
When the LLM must process natural language, the pipeline remains effective: it matches the preference-learning gold-feature oracle on Flight and reaches 90.8\% / 97.6\% on adversarial Naive Bayes / HMM inputs across five task-set seeds, two families held out from the reusable-template registry.

\textbf{Contributions.}
\begin{itemize}
    \item \textbf{Diagnostic}: PCD shows that LLM probabilistic reasoning fails primarily in computation, not in parsing or final decision-making.
    \item \textbf{System}: a typed \taskspec{} interface, deterministic compiler, deploy check, and registry turn LLM-assembled family specifications into reusable exact solvers.
    \item \textbf{Evidence}: the system spans preference learning, bandits, Bayesian networks, Naive Bayes, and HMM forward filtering, with exact backend checks, natural-language E2E gains beyond the reusable-template registry, and an external QUITE comparison.
\end{itemize}

\section{Task families and evaluation setting}
\label{sec:background}
% ============================================================

We study tasks where an input describes observations, a probabilistic model, and a query or decision.
Solving the task requires two different abilities: recover the structured model from the input, then run the appropriate inference algorithm.
The second step varies by family: preference learning uses hypothesis enumeration, bandits use conjugate updates, Bayesian networks use variable elimination, Naive Bayes uses class-posterior normalization, and HMMs use forward filtering.

This distinction matters because a solver induced for a \emph{family} should handle many instances: different feature counts, observation lengths, network topologies, or evidence assignments.
We therefore report backend checks separately from natural-language end-to-end results.
Backend checks ask whether the compiled solver is exact once the LLM-assembled specification is valid.
End-to-end results include the LLM-facing steps: family recognition, parsing or \taskspec{} induction, compilation, and solving.

Our evaluation covers Flight/Hotel preference learning ($n{=}748$), TextBandit-style histories~\citep{lim2025textbandit} ($n{=}100$), BLInD Bayesian networks ($n{=}900$), standard bnlearn networks (400 finite backend queries and 120 PAL stress-test queries), QUITE external Bayesian-inference queries, template-registry held-out Naive Bayes and HMM tasks, and a mixed E2E benchmark over six input streams.
Appendix~\ref{app:families} summarizes the families and datasets.

\section{PCD: Diagnosing the Compute Bottleneck}
\label{sec:pcd}
% ============================================================

\subsection{Method: Gold-Injection Interventions}

We decompose probabilistic reasoning into three stages with well-defined interfaces.
For each task, a gold oracle supplies the structured representation, the exact posterior or expected utilities, and the resulting optimal action.
PCD then runs three interventions: \textbf{Parse} asks the model to recover the structured inputs; \textbf{Compute$\mid$GoldParse} gives it the gold structure and scores the result of carrying out the probabilistic computation; \textbf{Decide$\mid$GoldPosterior} gives it the gold posterior or utilities and scores the final action.
For an instance $x$, write the gold pipeline as
\begin{equation}
s^*=\mathcal{P}^*(x),\qquad z^*=\mathcal{C}^*(s^*),\qquad a^*=\mathcal{D}^*(z^*),
\label{eq:pcd_gold}
\end{equation}
where $s^*$ is the structured problem representation, $z^*$ is the posterior or expected utility vector, and $a^*$ is the final answer.
PCD scores an LLM by replacing one stage at a time with its gold input:
\begin{equation}
\begin{aligned}
\mathrm{Parse} &= \mathbf{1}\{\mathcal{P}_\psi(x)=s^*\},\\
\mathrm{Compute}\mid\mathrm{GoldParse} &= \mathbf{1}\{d(\mathcal{C}_\psi(s^*),z^*)\le \epsilon\},\\
\mathrm{Decide}\mid\mathrm{GoldPosterior} &= \mathbf{1}\{\mathcal{D}_\psi(z^*)=a^*\}.
\end{aligned}
\label{eq:pcd_scores}
\end{equation}
Parse is scored by exact field match.
For probability queries, Compute is scored by numerical tolerance; for preference learning, it is scored by whether the model's self-computed posterior expected utilities lead to the gold recommendation.
Decide is scored after injecting the gold posterior or expected utilities directly.
A signature of $\text{ParseAcc} \approx 1,\; \text{DecAcc} \approx 1,\; \text{CompAcc} \ll 1$ indicates a compute bottleneck.
We observe this pattern across every model and task.

\subsection{Results: A Consistent Compute Bottleneck}

On preference learning, Compute ranges from 28\% for GPT-4o-mini to 78\% for Opus, while Decide = 100\% for every model.
On BN inference, the same pattern holds and amplifies with depth: Compute drops from $\sim$82\% at depth 2 to single digits by depth 10, while Parse stays $\geq$96\% and Decide at 100\%.
The same signature recurs across task families, including the template-registry held-out Naive Bayes and HMM families evaluated in \S\ref{sec:held_out}.
Scaling helps, but not enough: upgrading from GPT-4o-mini to GPT-5.4 (a $67\times$ price increase) improves Compute by only 9 percentage points on BN inference; at depth 10, GPT-5.4 still produces the wrong answer 89\% of the time.
These results motivate a system that uses the LLM's strong parsing ability while bypassing its weak computation entirely.

\section{Compile-once solver induction}
\label{sec:method}
% ============================================================

PCD tells us what not to do: do not ask the LLM to carry out probabilistic inference token by token.
Our method instead asks the LLM to induce a compact solver specification for the task family.
The compiler owns the numerical computation.

\subsection{TaskSpec and typed operations}

A \taskspec{} is a declarative JSON object that names the inference family, state structure, observation model, and decision rule.
The inductor fills this object from a few examples.
For Flight preference learning, for instance, it specifies a hypothesis-enumeration problem over a feature-weight space; the compiler then constructs the posterior update and expected-utility decision rule.
For Bayesian networks, it specifies variables, CPT factors, query, and evidence; the compiler invokes variable elimination.

\paragraph{What is assembled by the LLM?}
The DSL defines the semantics of typed atoms, just as a probabilistic programming language defines factor product or marginalization.
The task-specific solver logic is supplied through the LLM-assembled \taskspec{} rather than per-instance generated implementation code.
The inductor selects and composes a route over the fixed typed interface, binds the state and observation structure, chooses the decision rule, and supplies family parameters when they are part of the family description.
Compilation turns that assembly into an executable solver object; after validation, later instances reuse the same compiled route and only bind instance-level observations, evidence, or query fields.
Thus ``compile once'' means that one validated LLM assembly can serve many later natural-language instances.

The backend exposes seven typed operations:
\texttt{condition}, \texttt{multiply}, \texttt{marginalize}, \texttt{normalize}, \texttt{enumerate\_hypotheses}, \texttt{expectation}, and \texttt{argmax}.
Three reusable templates compose these operations for common inference patterns: \texttt{softmax\_pref}, \texttt{beta\_bernoulli}, and \texttt{ve\_query}.
Families without a template can still be represented through explicit fields and core-operation routes, which is how we handle Naive Bayes and HMM forward filtering.
This vocabulary is fixed in our experiments, but the interface is extensible: a new primitive or macro must expose a typed signature and pass the same deploy checks before it can enter the registry.
Appendices~\ref{app:dsl}--\ref{app:taskspec} give the operator definitions and schema.

\subsection{Induction, verification, and reuse}

The inductor is called once per solver specification, not once per instance.
It recognizes the family, decides whether to instantiate a reusable template or a core-op route, and emits a complete \taskspec{}.
The compiler is deterministic: the same specification always yields the same solver.
Formally, for family examples $\mathcal{E}_F$ and later instance $x$, the intended division of labor is
\begin{equation}
\tau_F = I_\psi(\mathcal{E}_F),\qquad S_F=\mathrm{Compile}(\tau_F),\qquad \hat{y}=S_F(R_\psi(x)),
\label{eq:compile_once}
\end{equation}
where the LLM inductor $I_\psi$ is used once to produce a solver specification $\tau_F$, $R_\psi$ only routes or parses later natural-language instances, and the compiled solver $S_F$ performs the probabilistic computation.
When validation labels are available, a two-gate deploy check requires the solver to execute and to match held-out references within the task tolerance.
Failures return diagnostics to the inductor for up to three refinement rounds.

Once a solver passes validation, the implementation stores it in a registry keyed by family and schema.
At run time, the router first consults this registry: a hit dispatches directly to the cached solver, while a miss can trigger a new induction-and-validation round whose successful route grows the registry.
Later same-family instances may still require LLM parsing, but inference no longer happens inside the LLM.
The mixed E2E router composes the registered supported routes with an unsupported-reject branch.

\section{Experiments}
\label{sec:experiments}
% ============================================================

The experiments answer three questions.
First, is the bottleneck really computation, or can stronger per-instance tools remove it?
Second, does the typed interface extend beyond the macros it was designed with?
Third, does the full natural-language pipeline compose when routing, parsing, compilation, and solving are all active?
We keep three kinds of evidence separate.
PCD is diagnostic: it identifies computation as the failure mode.
Backend checks isolate compiled-solver correctness once an LLM-assembled specification has passed the deploy interface.
Natural-language E2E results are stricter: they include family recognition, parsing or induction, compilation, and solving.
Baselines are direct answering, per-instance PAL code generation~\citep{gao2023pal}, and compile-time code generation from a few examples.

\subsection{Can per-instance code generation replace a compiler?}

BLInD's small binary networks are the most favorable setting for PAL: generated programs are short and the state space is tractable.
Even there, GPT-4o-mini PAL collapses from 93\% at depth~2 to 2\% at depth~10 (Appendix~\ref{app:pal_depth}).
GPT-5.4 PAL is much stronger at 98.1\% overall, but it pays per query and still makes errors.
Compile-time code generation shows the same split: GPT-5.4 writes a reusable VE solver after one repair round, whereas GPT-4o-mini fails after five rounds and scores 0\% on all 900 BLInD problems.
The DSL path removes the hard part from the LLM: once GPT-4o-mini induces a valid \taskspec{}, the compiled solver matches all BLInD references.

The gap widens on real-world networks.
We evaluate four standard bnlearn networks~\citep{scutari2010bnlearn}: Asia (8 nodes), Child (20 nodes), Insurance (27 nodes), and Alarm (37 nodes), with multi-valued categorical variables and larger factor products.

On Asia, PAL with GPT-5.4 still reaches 90\%, but \textbf{on networks with $\geq$20 nodes it drops to 0\% on Child, 3\% on Insurance, and 0\% on Alarm}; GPT-4o-mini is low overall (17.5\%) and also reaches 0\% on Alarm (Figure~\ref{fig:scaling_cost}).
Only 27--29\% of generated programs execute successfully overall: the variable-elimination code often crashes on multi-valued CPTs, deep elimination chains, and complex factor products.
In contrast, the VSI compiled solver matches pgmpy variable-elimination references on \textbf{400/400} finite bnlearn queries (100 per network; Wilson 95\% CI [99.0, 100.0]).
We therefore use bnlearn as a structured external backend check, a registered-network parse-and-solve test, and a stress test for per-instance code generation.
A registered-network E2E check, where GPT-4o-mini extracts the network key, evidence, and query variable before dispatching to the compiled solver, reaches 79/80 strict single-label accuracy (98.8\%, Wilson 95\% CI [93.3, 99.8]); the sole mismatch is an exact MAP tie under the pgmpy reference posterior.
The gap between per-instance generation and compiled solvers widens sharply as networks become larger and multi-valued.

\paragraph{External check on QUITE.}
The bnlearn experiments use structured network definitions.
To test the same registered-solver pattern on a separate natural-language Bayesian-inference corpus, we build a QUITE split~\citep{schrader2024quite}.
The network is loaded once from QUITE's structured Problog artifact, and the LLM only maps short natural-language evidence/query text to variable and state names; exact posterior inference is then run by the VSI compiled solver.
Figure~\ref{fig:scaling_cost}c,d use the same 75 numeric queries for all methods.
VSI with GPT-4o-mini reaches 96.0\%, while direct GPT-5.4 reaches 60.0\% and PAL with GPT-5.4 reaches 88.0\% at roughly $300\times$ the API cost and $24\times$ the wall-clock time.

\subsection{Does the interface extend beyond reusable templates?}
\label{sec:held_out}

To test whether the interface can assemble solvers beyond its reusable templates, we freeze the template library and evaluate on two inference families held out from the reusable-template registry: Naive Bayes medical diagnosis (3--6 diseases, 4--8 symptoms, $n{=}200$) and HMM forward filtering (3--5 hidden states, 4--8 observation steps, $n{=}100$).
Neither family has a corresponding reusable template, so the LLM must assemble the solver route through explicit \taskspec{} fields and core-op-backed compositions.
The interface supplies typed extension slots, but not a family macro or executable solver recipe.
HMM is the stronger test: it requires \emph{sequential temporal reasoning} via iterated multiply--marginalize--normalize over a time axis, a pattern absent from all three template-backed routes.

% ============================================================
\section{Analysis}
\label{sec:analysis}
% ============================================================

The results above validate the compile-once pipeline; we now summarize why it works and what trust boundary it establishes.
A 23-strategy ablation on preference learning with 624 Flight samples and GPT-4o-mini provides independent evidence for the compute bottleneck (Appendix~\ref{app:strategies}).
Accuracy rises with the fraction of computation offloaded: pure CoT scores $\leq$33\%, at or below the 3-way random baseline; partial math injection reaches roughly 50--58\%; direct result injection reaches 74.8\%, matching the Oracle.
In short, the more math the LLM must do, the worse it performs.
Pure CoT is ineffective, confirming that self-reflection alone does not improve probabilistic computation.

Stronger models raise Compute accuracy, from 28\% to 78\% across six models, but none eliminate errors. Opus still fails on 22\% of preference instances, and GPT-5.4 reaches only 11\% at BN depth 10.
PAL with GPT-5.4 bridges part of the gap (98.1\% on BLInD and 88.0\% on QUITE) but still trails the compiled path while paying per query.
No model--tool combination tested guarantees correctness.
The approach is strongest when distributions are given or derivable; tasks that require estimating distributions from sparse context, as in DeLLMa~\citep{liu2025dellma}, call for complementary modeling components.

\section{Related Work}
\label{sec:related}
% ============================================================

\paragraph{Bayesian teaching and preference learning.}
Qiu et al.'s Bayesian Teaching study~\citep{qiu2026bayesian} showed that targeted training can make a language model more Bayesian on Flight/Hotel-style preference tasks.
We use that task family as a starting point but change the intervention: the model weights stay fixed, the LLM writes the reusable \taskspec{}, and the validated solver is reused on later instances.
The same interface then covers TextBandit-style updates, Bayesian networks, Naive Bayes, and HMM filtering.

\paragraph{Program-aided and tool-using LLMs.}
PAL~\citep{gao2023pal}, Program of Thoughts~\citep{chen2023pot}, Toolformer~\citep{schick2023toolformer}, ReAct~\citep{yao2023react}, and large-scale tool-routing systems such as Gorilla and ToolLLM~\citep{patil2024gorilla,qin2024toolllm} all put external computation behind an LLM interface.
Their unit of work is usually a single query: the model generates code or calls a tool for each instance.
This is effective for deterministic arithmetic, but it is brittle for probabilistic algorithms: on BLInD, GPT-4o-mini PAL accuracy drops from 93\% at depth~2 to 2\% at depth~10, while GPT-5.4 PAL remains strong but still pays per query and fails sharply on larger bnlearn networks (Appendix~\ref{app:pal_depth}).
Our inductor instead emits a typed family specification once; after verification, the compiled solver runs without LLM calls.
This also differs from schema-constrained per-instance parsing into an existing library, including grammar-constrained semantic parsers like TRANX~\citep{yin2018tranx}: \method{} makes the LLM assemble and validate the reusable solver route, then amortizes that route across later inputs.

\paragraph{Formal solvers for reasoning.}
SatLM~\citep{ye2023satlm}, Logic-LM~\citep{pan2023logiclm}, LINC~\citep{olausson2023linc}, Logic.py~\citep{kesseli2025logicpy}, and constraint-programming translators~\citep{michailidis2024cp} map natural language to formal solvers for logical or combinatorial problems.
We take the same trust-boundary lesson---make the LLM fill a constrained representation, then let a solver execute it---but the target operations are probabilistic: factor products, marginalization, normalization, posterior expectations, and decisions.
BLInD~\citep{nafar2025blind}, QUITE~\citep{schrader2024quite}, and distributional-question benchmarks~\citep{paruchuri2024odds} expose this probabilistic setting from the evaluation side; our contribution is to turn the diagnostic into a reusable solver interface.

\paragraph{Probabilistic programming and graphical-model toolkits.}
Probabilistic programming systems and graphical-model libraries such as ProbLog~\citep{deraedt2007problog,fierens2015problog2}, Stan~\citep{carpenter2017stan}, Pyro~\citep{bingham2019pyro}, Gen~\citep{cusumanotowner2019gen}, and pgmpy~\citep{ankan2015pgmpy} provide mature inference machinery once a model is expressed in the required formal language.
Recent natural-language-to-probabilistic-program work, including LLM-BI~\citep{huang2025llmbi} and NL-to-PLoT translation~\citep{wong2023word}, moves part of that specification burden to language models.
\method{} targets the complementary interface problem: the LLM assembles a typed finite-discrete solver route from reusable primitives, deploy checks exercise the route and match references when available, and the resulting solver is cached for later same-family instances rather than regenerated per query.

\paragraph{Library learning and program induction.}
DreamCoder~\citep{ellis2021dreamcoder}, LILO~\citep{grand2024lilo}, FunSearch~\citep{romeraparedes2024funsearch}, PIPS~\citep{stein2025pips}, and agentic-skill systems~\citep{zhang2026evoskills} learn or search reusable computational structure.
Our setting makes this idea directly checkable for probabilistic reasoning: the induced object is a typed \taskspec{} that compiles into a deterministic solver, rather than arbitrary code.
DisCIPL~\citep{lew2025discipl} and LLM-guided POMDP induction~\citep{curtis2025pomdp} share the idea of using LLMs as inductors, but keep different targets in view---text generation control and online planning rather than exact discrete inference.

% ============================================================
\section{Scope and Future Work}
\label{sec:limitations}
% ============================================================

\paragraph{Scope.}
\method{} targets exact inference over finite discrete distributions, a broad and auditable setting that covers Bayesian networks, preference learning, bandits, Naive Bayes, and HMM forward filtering.
The same interface can incorporate additional typed atoms for continuous variables, approximate inference, or distribution learning from sparse unstructured context.
The evidence spans five inference families across eight datasets, plus an external QUITE benchmark that reuses the same registered-solver interface.
It includes five adversarial task-set seeds for NB ($n{=}600$) and HMM ($n{=}500$), two families held out from the reusable-template registry and solved through LLM-assembled core-op routes.
The mixed E2E benchmark stress-tests route-and-solve composition over supported input streams plus unsupported examples; enlarging that stream is a data and validation-suite question rather than a change to the compiler interface.

\paragraph{Diagnostics and Induction.}
PCD is an interventional diagnostic: Compute$\mid$GoldParse intentionally measures whether a model can select and execute the required probabilistic calculation once structure is fixed.
Its stage boundaries are deliberately coarse enough to be reused across task families, and the observed pattern is stable across models, tasks, and BN depths.
Decide$\mid$GoldPosterior isolates the posterior-to-action step used by these tasks; its high score shows that final action selection is not the bottleneck.
Family-level induction is a stronger capability than instance-level parsing, and our experiments validate it through deploy checks, template-registry held-out families, and mixed E2E composition.

\paragraph{Extensibility and Verification.}
The operator basis is deliberately small: seven typed operations plus three reusable templates.
This makes the trust boundary inspectable and lets new families either reuse core operations, as NB/HMM do, or add typed primitives behind the same validation loop.
Verification is operational: deploy gates execute the compiled solver and require agreement with published or programmatic reference solvers before the solver is stored in the registry.
Induction uses a stochastic LLM only at compile time; once a specification passes validation, later inference is deterministic.
The supplementary artifact includes prompts, specifications, and compiled solvers.

% ============================================================
\section{Conclusion}
\label{sec:conclusion}
% ============================================================

LLMs are useful probabilistic interfaces, but poor probabilistic calculators.
PCD makes this failure mode visible: models often recover structure and act correctly from a posterior, yet fail at the computation itself.
\method{} uses that diagnosis to change the role of the LLM.
The model induces a typed family specification; the compiled solver performs inference and can be reused across instances.

The evidence supports this division of labor across five inference families and an external QUITE benchmark.
Backend exactness, natural-language robustness, and mixed routing composition are measured separately, making the claim precise rather than anecdotal.
Within finite discrete inference, the result is a practical compiler abstraction for LLM probabilistic reasoning: language models identify reusable structure; validated solvers do the math.

\section{Detailed PCD Protocol}
\label{app:pcd_protocol}

Each PCD stage uses a separate LLM call with the following structure:

\paragraph{Parse.}
The LLM receives the full natural-language problem and is asked to extract structured inputs in a specified JSON format.
For BN inference: variable names, parent--child edges, conditional probability tables, query variable, and evidence assignments.
For preference learning: feature names, option feature vectors per round, and user choices.
The extracted structure is compared field-by-field against the gold parse; a sample is scored correct only if all fields match.

\paragraph{Compute$\mid$GoldParse.}
The LLM receives the \emph{gold} structured inputs (not its own parse) and is asked to perform the probabilistic computation.
For BN inference: compute $P(\text{query} \mid \text{evidence})$ via variable elimination.
For preference learning: compute posterior-weighted expected utilities for each option.
BN outputs are compared against the gold probability with tolerance $\epsilon = 0.01$.
Preference outputs are scored by whether the model's self-computed utilities imply the gold recommendation.

\paragraph{Decide$\mid$GoldPosterior.}
The LLM receives the \emph{gold} computed posterior (or expected utilities) and is asked to make a decision.
For BN inference: report the most likely value of the query variable.
For preference learning: recommend the option with the highest expected utility.
The output is compared against the gold decision.

All prompts use zero temperature where supported, \texttt{max\_\allowbreak tokens}=1024--8192 depending on task complexity, via the OpenRouter API gateway.
Model identifiers: \texttt{openai/\allowbreak gpt-4o-mini}, \texttt{openai/\allowbreak gpt-4o}, \texttt{openai/\allowbreak gpt-5.4}, \texttt{anthropic/\allowbreak claude-sonnet-4}, \texttt{anthropic/\allowbreak claude-opus-4-6}, \texttt{google/\allowbreak gemini-3.1-pro}.
All LLM calls use the OpenRouter API gateway; exact prompt templates, model identifiers, and runner metadata are included in the supplementary artifact.

\section{DSL Specification}
\label{app:dsl}

\paragraph{Types.}
The DSL defines four core types:
\begin{itemize}
    \item \texttt{Distribution}: a discrete probability distribution over a finite support set, stored as aligned arrays of values and probabilities (non-negative, summing to~1).
    \item \texttt{Factor}: a multi-variable probabilistic factor mapping variable-assignment tuples to non-negative reals. Variable domains are inferred from table keys.
    \item \texttt{HypothesisSpace}: defines a set of hypotheses, either as a Cartesian product of per-dimension value lists or as an explicit enumeration.
    \item \texttt{Evidence}: a generic container for observations. Concrete subtypes include variable assignments for BN inference, choice indices for preference learning, and arm/reward pairs for bandits.
\end{itemize}

\paragraph{Core Operations (7 typed ops).}
Each operation is defined over the type system $\mathbb{T} = \{\texttt{Factor}, \texttt{Distribution}, \texttt{HypothesisSpace}, \texttt{Evidence}\}$.
Let $\phi: \text{Scope}(\phi) \to \mathbb{R}_{\geq 0}$ denote a factor over variables $\text{Scope}(\phi)$, and $\mathbf{e}$ an evidence assignment.
\begin{align}
\texttt{condition}(\phi, \mathbf{e})(\mathbf{x}) &= \begin{cases} \phi(\mathbf{x}) & \text{if } \mathbf{x} \text{ consistent with } \mathbf{e}, \\ 0 & \text{otherwise}; \end{cases} \label{eq:op_condition} \\[3pt]
\texttt{multiply}(\phi_1, \ldots, \phi_n)(\mathbf{x}) &= \prod_{i=1}^{n} \phi_i\!\left(\mathbf{x}_{\text{Scope}(\phi_i)}\right); \label{eq:op_multiply} \\[3pt]
\texttt{marginalize}(\phi, \mathbf{V})(\mathbf{x}_{\text{Scope}(\phi) \setminus \mathbf{V}}) &= \sum_{\mathbf{v} \in \text{Dom}(\mathbf{V})} \phi(\mathbf{x}_{\text{Scope}(\phi) \setminus \mathbf{V}}, \mathbf{v}); \label{eq:op_marginalize} \\[3pt]
\texttt{normalize}(\phi)(x) &= \phi(x) \Big/ \sum_{x'} \phi(x'); \label{eq:op_normalize} \\[3pt]
\texttt{enumerate}(\Theta) &= \bigtimes_{d=1}^{D} \mathcal{V}_d, \quad \text{where } \Theta = \mathcal{V}_1 \times \cdots \times \mathcal{V}_D; \label{eq:op_enum} \\[3pt]
\texttt{expectation}(p, f) &= \sum_{x \in \text{Supp}(p)} p(x) \cdot f(x); \label{eq:op_expect} \\[3pt]
\texttt{argmax}(\{a_j \mapsto v_j\}) &= a_{j^*}, \quad j^* = \arg\max_j v_j. \label{eq:op_argmax}
\end{align}

\paragraph{Family Macros (3 syntactic sugar).}
Each macro composes core operations for a common inference pattern.
For example, \texttt{ve\_query} implements variable elimination as:
\begin{equation}
\texttt{ve\_query} = \texttt{normalize} \circ \texttt{marginalize}_{\mathbf{H}} \circ \texttt{multiply}_{i=1}^{n} \circ \texttt{condition}_{\mathbf{e}},
\label{eq:macro_ve}
\end{equation}
where the marginalization iterates over hidden variables $\mathbf{H}$ in a chosen elimination ordering.
Similarly, \texttt{softmax\_pref} composes \texttt{enumerate} $\to$ \texttt{multiply} (softmax likelihoods) $\to$ \texttt{normalize} $\to$ \texttt{expectation} $\to$ \texttt{argmax}, and \texttt{beta\_bernoulli} applies conjugate updates via \texttt{condition} $\to$ \texttt{normalize} $\to$ \texttt{argmax}.
On template-registry held-out HMM forward filtering (\S\ref{sec:held_out}), the system uses a core-op-backed route over time that does not correspond to any existing macro.

\section{Compile-Time Baseline Failure Analysis}
\label{app:compile_failure}

GPT-4o and GPT-4o-mini both fail to produce working VE solvers via unconstrained code generation, even with 5 rounds of self-repair. We analyze the failure modes below.

\paragraph{GPT-4o: algorithmic errors in variable elimination.}
GPT-4o generates code with multiple algorithmic bugs: the CPT parsing regex is too greedy, failing on multi-condition entries; factor construction assigns identical tuples regardless of parent values; and the \texttt{sum\_out} function treats tuple-based assignments as dictionaries, causing \texttt{KeyError}.
Across 5 repair rounds, GPT-4o outputs \emph{identical} code (9,589 characters) every round, unable to diagnose its own bugs from the error feedback.

\paragraph{GPT-4o-mini: data structure mismatch.}
GPT-4o-mini's solver crashes with \texttt{KeyError} on graph parsing.
The generated code expects string-keyed dictionaries but receives tuple-keyed CPTs.
Like GPT-4o, self-repair produces nearly identical code across all 5 rounds.

\paragraph{Implications.}
These failures are not prompt engineering artifacts: both models receive the same 5 training examples and the same self-repair protocol as GPT-5.4, which succeeds after 1 repair round.
These failures stem from the difficulty of implementing correct VE in unconstrained Python: subtle algorithmic choices in CPT representation, factor product semantics, and elimination ordering must all be simultaneously correct.
VSI eliminates this failure mode by constraining the inductor to a declarative specification, shifting the burden of correct implementation to the deterministic compiler.
