                                                         Abstract
 1             Large language models (LLMs) are increasingly used as natural-language inter-
 2             faces for probabilistic reasoning, but end-to-end evaluations often conflate failures
 3             of parsing, probabilistic computation, and decision-making. We make two contri-
 4             butions. First, we introduce Parse–Compute–Decide (PCD), a gold-intervention
 5             diagnostic that isolates these stages by supplying gold structure or gold poste-
 6             riors. Across six LLMs and several probabilistic tasks, models usually recover
 7             task structure and choose correct actions from a posterior, but remain unreliable
 8             probabilistic calculators: compute-stage accuracy ranges from 28% to 78% on
 9             preference learning and drops to 3–11% on depth-10 Bayesian networks. Second,
10             we propose Verified Solver Induction (VSI), a compile-once, reuse-many frame-
11             work for reliable LLM-assisted probabilistic reasoning. Unlike direct prompting or
12             per-instance PAL, VSI changes the role of the LLM from a per-instance calculator
13             or code generator into a task-family-level solver inducer: an off-the-shelf LLM
14             assembles a reusable typed solver specification from probabilistic atoms and infer-
15             ence routes. A deterministic compiler lowers the specification into an executable
16             solver for finite discrete models, runs acceptance checks and compares against
17             references when available, and caches accepted solvers for future same-family
18             instances. At run time, accepted compiled solvers perform exact inference rather
19             than the LLM. We evaluate VSI on preference learning, bandits, Bayesian net-
20             works, Naive Bayes, and HMM filtering. VSI matches reference solvers on 1,150
21             Flight/BLInD instances and 400 finite-query bnlearn checks. On external QUITE
22             queries, VSI reaches 96.0%, compared with 36.0–60.0% for direct answering and
23             24.0–88.0% for per-instance PAL. On natural-language Naive Bayes and HMM
24             tasks, VSI reaches 90.8% and 97.6%, while direct LLM computation reaches only
25             18.2% and 32.4% even from structured inputs. Together, PCD identifies probabilis-
26             tic computation as the bottleneck, and VSI turns LLMs from brittle probabilistic
27             calculators into compile-time inducers of solver-backed probabilistic interfaces
28             without fine-tuning.


29   1    Introduction
30   Ask a frontier LLM to solve a ten-node Bayesian network by variable elimination and it answers
31   correctly only 11% of the time. Ask the same model to identify the variables, conditional probability
32   tables, evidence, and query, and it succeeds on nearly all instances [18]. This is the failure mode
33   we study: the model often understands the problem but cannot reliably execute the probabilistic
34   computation.
35   The usual fixes do not quite address this abstraction gap. Chain-of-thought [30] leaves the model
36   doing the math. Program-aided prompting asks the model to write new code for each instance.
37   Bayesian Teaching, introduced on the Flight/Hotel preference tasks [24], takes a training-side route:

38   fine-tune a model to follow Bayesian demonstrations. Family-specific tools such as ProbLog for
39   Bayesian networks [18, 7] solve one benchmark family at a time. A per-instance parser-to-library
40   pipeline is safer than free-form code, but it still treats each input as a fresh extraction problem. Our
41   question is different: can an off-the-shelf LLM, with no weight updates, write a reusable solver by
42   composing typed probabilistic atoms, pass a deploy check once, and then reuse the compiled solver
43   across future instances?
44   We first show why this is the right split. Parse–Compute–Decide (PCD) isolates three stages
45   by injecting gold intermediate results: Parse tests structure extraction; Compute|GoldParse tests
46   numerical inference given perfect structure; Decide|GoldPosterior tests the final action given the
47   correct posterior. Across six models, Parse is usually high and Decide is essentially solved, but
48   Compute remains poor: 28–78% on preference learning and only 3–11% at depth 10 on BLInD
49   Bayesian networks. The problem is not simply that the model cannot read the task; it is that
50   probabilistic inference is the wrong thing to leave inside the language model.
51   We therefore build the LLM-facing interface as a compiler target rather than a prompt. We call this
52   approach Verified Solver Induction (VSI). The LLM writes a declarative TaskSpec for a task family,
53   effectively assembling a solver from typed probabilistic building blocks. A deterministic compiler
54   lowers that specification to a small typed probabilistic DSL, validates the resulting solver against
55   held-out labels when available, and stores it for reuse (Figure 1). Later instances from the same
56   family can be parsed and solved without asking the LLM to perform inference.
57   This design gives a clean separation between backend correctness, language-interface robustness, and
58   routing composition. Given LLM-assembled specifications that pass the deploy check, the compiled
59   solvers match references on Flight/BLInD and finite-query bnlearn checks, including standard multi-
60   valued bnlearn networks where per-instance generated code is unreliable. On QUITE, a separate
61   external Bayesian-inference corpus, the registered-network VSI path reaches 96.0% on the same
62   75-query split, compared with 60.0% for direct GPT-5.4 and 88.0% for PAL with GPT-5.4. When the
63   LLM must process natural language, the pipeline remains effective: it matches the preference-learning
64   gold-feature oracle on Flight and reaches 90.8% / 97.6% on adversarial Naive Bayes / HMM inputs
65   across five task-set seeds, two families held out from the reusable-template registry.

74    2     Task families and evaluation setting
75    We study tasks where an input describes observations, a probabilistic model, and a query or decision.
76    Solving the task requires two different abilities: recover the structured model from the input, then
77    run the appropriate inference algorithm. The second step varies by family: preference learning uses
78    hypothesis enumeration, bandits use conjugate updates, Bayesian networks use variable elimination,
79    Naive Bayes uses class-posterior normalization, and HMMs use forward filtering.
80    This distinction matters because a solver induced for a family should handle many instances: different
81    feature counts, observation lengths, network topologies, or evidence assignments. We therefore report
82    backend checks separately from natural-language end-to-end results. Backend checks ask whether the
83    compiled solver is exact once the LLM-assembled specification is valid. End-to-end results include
84    the LLM-facing steps: family recognition, parsing or TaskSpec induction, compilation, and solving.
85    Our evaluation covers Flight/Hotel preference learning (n=748), TextBandit-style histories [15]
86    (n=100), BLInD Bayesian networks (n=900), standard bnlearn networks (400 finite backend queries
87    and 120 PAL stress-test queries), QUITE external Bayesian-inference queries, template-registry held-
88    out Naive Bayes and HMM tasks, and a mixed E2E benchmark over six input streams. Appendix A
89    summarizes the families and datasets.

90    3     PCD: Diagnosing the Compute Bottleneck
91    3.1   Method: Gold-Injection Interventions

92    We decompose probabilistic reasoning into three stages with well-defined interfaces. For each task, a
93    gold oracle supplies the structured representation, the exact posterior or expected utilities, and the
94    resulting optimal action. PCD then runs three interventions: Parse asks the model to recover the
95    structured inputs; Compute|GoldParse gives it the gold structure and scores the result of carrying
96    out the probabilistic computation; Decide|GoldPosterior gives it the gold posterior or utilities and
97    scores the final action. For an instance x, write the gold pipeline as
                               s∗ = P ∗ (x),      z ∗ = C ∗ (s∗ ),   a∗ = D∗ (z ∗ ),                      (1)
98    where s∗ is the structured problem representation, z ∗ is the posterior or expected utility vector, and
99    a∗ is the final answer. PCD scores an LLM by replacing one stage at a time with its gold input:
                                               Parse = 1{Pψ (x) = s∗ },
                                Compute | GoldParse = 1{d(Cψ (s∗ ), z ∗ ) ≤ ϵ},                           (2)
                               Decide | GoldPosterior = 1{Dψ (z ∗ ) = a∗ }.
100   Parse is scored by exact field match. For probability queries, Compute is scored by numerical
101   tolerance; for preference learning, it is scored by whether the model’s self-computed posterior
102   expected utilities lead to the gold recommendation. Decide is scored after injecting the gold posterior
103   or expected utilities directly. A signature of ParseAcc ≈ 1, DecAcc ≈ 1, CompAcc ≪ 1 indicates
104   a compute bottleneck. We observe this pattern across every model and task.

105   3.2   Results: A Consistent Compute Bottleneck

106   On preference learning, Compute ranges from 28% for GPT-4o-mini to 78% for Opus, while Decide =
107   100% for every model. On BN inference, the same pattern holds and amplifies with depth: Compute
108   drops from ∼82% at depth 2 to single digits by depth 10, while Parse stays ≥96% and Decide
109   at 100%. The same signature recurs across task families, including the template-registry held-out
110   Naive Bayes and HMM families evaluated in §5.2. Scaling helps, but not enough: upgrading from
111   GPT-4o-mini to GPT-5.4 (a 67× price increase) improves Compute by only 9 percentage points on

115   4                  Compile-once solver induction
116   PCD tells us what not to do: do not ask the LLM to carry out probabilistic inference token by token.
117   Our method instead asks the LLM to induce a compact solver specification for the task family. The
118   compiler owns the numerical computation.

119   4.1                TaskSpec and typed operations

120   A TaskSpec is a declarative JSON object that names the inference family, state structure, observation
121   model, and decision rule. The inductor fills this object from a few examples. For Flight preference
122   learning, for instance, it specifies a hypothesis-enumeration problem over a feature-weight space;
123   the compiler then constructs the posterior update and expected-utility decision rule. For Bayesian
124   networks, it specifies variables, CPT factors, query, and evidence; the compiler invokes variable
125   elimination.

126   What is assembled by the LLM? The DSL defines the semantics of typed atoms, just as a
127   probabilistic programming language defines factor product or marginalization. The task-specific
128   solver logic is supplied through the LLM-assembled TaskSpec rather than per-instance generated
129   implementation code. The inductor selects and composes a route over the fixed typed interface, binds
130   the state and observation structure, chooses the decision rule, and supplies family parameters when
131   they are part of the family description. Compilation turns that assembly into an executable solver
132   object; after validation, later instances reuse the same compiled route and only bind instance-level
133   observations, evidence, or query fields. Thus “compile once” means that one validated LLM assembly
134   can serve many later natural-language instances.
135   The backend exposes seven typed operations: condition, multiply, marginalize, normalize,
136   enumerate_hypotheses, expectation, and argmax. Three reusable templates compose these
137   operations for common inference patterns: softmax_pref, beta_bernoulli, and ve_query. Fam-
138   ilies without a template can still be represented through explicit fields and core-operation routes,
139   which is how we handle Naive Bayes and HMM forward filtering. This vocabulary is fixed in our
140   experiments, but the interface is extensible: a new primitive or macro must expose a typed signature
141   and pass the same deploy checks before it can enter the registry. Appendices F–G give the operator
142   definitions and schema.

143   4.2   Induction, verification, and reuse

144   The inductor is called once per solver specification, not once per instance. It recognizes the family,
145   decides whether to instantiate a reusable template or a core-op route, and emits a complete TaskSpec.
146   The compiler is deterministic: the same specification always yields the same solver. Formally, for
147   family examples EF and later instance x, the intended division of labor is

                         τF = Iψ (EF ),       SF = Compile(τF ),          ŷ = SF (Rψ (x)),                  (3)

148   where the LLM inductor Iψ is used once to produce a solver specification τF , Rψ only routes
149   or parses later natural-language instances, and the compiled solver SF performs the probabilistic
150   computation. When validation labels are available, a two-gate deploy check requires the solver to
151   execute and to match held-out references within the task tolerance. Failures return diagnostics to the
152   inductor for up to three refinement rounds.
153   Once a solver passes validation, the implementation stores it in a registry keyed by family and schema.
154   At run time, the router first consults this registry: a hit dispatches directly to the cached solver, while
155   a miss can trigger a new induction-and-validation round whose successful route grows the registry.
156   Later same-family instances may still require LLM parsing, but inference no longer happens inside
157   the LLM. The mixed E2E router composes the registered supported routes with an unsupported-reject
158   branch.


159   5     Experiments

160   The experiments answer three questions. First, is the bottleneck really computation, or can stronger
161   per-instance tools remove it? Second, does the typed interface extend beyond the macros it was
162   designed with? Third, does the full natural-language pipeline compose when routing, parsing,
163   compilation, and solving are all active? We keep three kinds of evidence separate. PCD is diagnostic:
164   it identifies computation as the failure mode. Backend checks isolate compiled-solver correctness
165   once an LLM-assembled specification has passed the deploy interface. Natural-language E2E results
166   are stricter: they include family recognition, parsing or induction, compilation, and solving. Baselines
167   are direct answering, per-instance PAL code generation [10], and compile-time code generation from
168   a few examples.

169   5.1   Can per-instance code generation replace a compiler?

170   BLInD’s small binary networks are the most favorable setting for PAL: generated programs are short
171   and the state space is tractable. Even there, GPT-4o-mini PAL collapses from 93% at depth 2 to 2%
172   at depth 10 (Appendix H). GPT-5.4 PAL is much stronger at 98.1% overall, but it pays per query and
173   still makes errors. Compile-time code generation shows the same split: GPT-5.4 writes a reusable VE
174   solver after one repair round, whereas GPT-4o-mini fails after five rounds and scores 0% on all 900
175   BLInD problems. The DSL path removes the hard part from the LLM: once GPT-4o-mini induces a
176   valid TaskSpec, the compiled solver matches all BLInD references.
177   The gap widens on real-world networks. We evaluate four standard bnlearn networks [28]: Asia (8
178   nodes), Child (20 nodes), Insurance (27 nodes), and Alarm (37 nodes), with multi-valued categorical
179   variables and larger factor products.
180   On Asia, PAL with GPT-5.4 still reaches 90%, but on networks with ≥20 nodes it drops to 0% on
181   Child, 3% on Insurance, and 0% on Alarm; GPT-4o-mini is low overall (17.5%) and also reaches
182   0% on Alarm (Figure 4). Only 27–29% of generated programs execute successfully overall: the
183   variable-elimination code often crashes on multi-valued CPTs, deep elimination chains, and complex
184   factor products. In contrast, the VSI compiled solver matches pgmpy variable-elimination references
185   on 400/400 finite bnlearn queries (100 per network; Wilson 95% CI [99.0, 100.0]). We therefore
186   use bnlearn as a structured external backend check, a registered-network parse-and-solve test, and a
187   stress test for per-instance code generation. A registered-network E2E check, where GPT-4o-mini
188   extracts the network key, evidence, and query variable before dispatching to the compiled solver,
189   reaches 79/80 strict single-label accuracy (98.8%, Wilson 95% CI [93.3, 99.8]); the sole mismatch is
190   an exact MAP tie under the pgmpy reference posterior. The gap between per-instance generation and
191   compiled solvers widens sharply as networks become larger and multi-valued.

192   External check on QUITE. The bnlearn experiments use structured network definitions. To test
193   the same registered-solver pattern on a separate natural-language Bayesian-inference corpus, we
194   build a QUITE split [27]. The network is loaded once from QUITE’s structured Problog artifact, and
195   the LLM only maps short natural-language evidence/query text to variable and state names; exact
196   posterior inference is then run by the VSI compiled solver. Figure 4c,d use the same 75 numeric
197   queries for all methods. VSI with GPT-4o-mini reaches 96.0%, while direct GPT-5.4 reaches 60.0%
198   and PAL with GPT-5.4 reaches 88.0% at roughly 300× the API cost and 24× the wall-clock time.

199   5.2   Does the interface extend beyond reusable templates?

200   To test whether the interface can assemble solvers beyond its reusable templates, we freeze the
201   template library and evaluate on two inference families held out from the reusable-template registry:
202   Naive Bayes medical diagnosis (3–6 diseases, 4–8 symptoms, n=200) and HMM forward filtering (3–
203   5 hidden states, 4–8 observation steps, n=100). Neither family has a corresponding reusable template,
204   so the LLM must assemble the solver route through explicit TaskSpec fields and core-op-backed
205   compositions. The interface supplies typed extension slots, but not a family macro or executable
206   solver recipe. HMM is the stronger test: it requires sequential temporal reasoning via iterated
207   multiply–marginalize–normalize over a time axis, a pattern absent from all three template-backed
208   routes.
209   These results test whether the interface is more than a template selector. Naive Bayes and HMM
210   have no reusable family template, and HMM requires a repeated forward update that is absent from
211   the three template-backed routes. On the same five adversarial task-set seeds, GPT-4o-mini reaches
212   only 18.2% / 32.4% when asked to compute directly while returning valid JSON. The same model
213   reaches 90.8% / 97.6% when it emits a TaskSpec and lets the compiled solver compute. Given a valid
214   TaskSpec, the core-op solvers match independent reference posteriors with maximum absolute error
215   below 10−9 . The remaining NB errors come from specification extraction on adversarial wording:
216   hedged probabilities, shuffled symptom order, and distractor clinical text.

247   7     Related Work

248   Bayesian teaching and preference learning. Qiu et al.’s Bayesian Teaching study [24] showed
249   that targeted training can make a language model more Bayesian on Flight/Hotel-style preference
250   tasks. We use that family as a starting point but change the intervention: model weights stay fixed, the
251   LLM writes a reusable TaskSpec, and the validated solver is reused across later instances. The same
252   interface covers TextBandit-style updates, Bayesian networks, Naive Bayes, and HMM filtering.

253   Program-aided and tool-using LLMs. PAL [10], Program of Thoughts [4], Toolformer [26],
254   ReAct [32], and large-scale tool-routing systems such as Gorilla and ToolLLM [22, 23] all put
255   external computation behind an LLM interface. Their unit of work is usually a single query: the
256   model generates code or calls a tool for each instance. This works for arithmetic but is brittle for


                                                            8
257   probabilistic algorithms: smaller-model PAL collapses with BLInD depth, and stronger PAL remains
258   costly and fails on larger bnlearn networks (Appendix H). VSI instead emits and validates a typed
259   family specification once, then amortizes reuse of the compiled route. It also differs from schema-
260   constrained per-instance parsing and grammar-constrained semantic parsers such as TRANX [34]:
261   reuse is part of the induced object.

262   Formal solvers for reasoning. SatLM [33], Logic-LM [20], LINC [19], Logic.py [14], and
263   constraint-programming translators [17] map natural language to formal solvers for logical or com-
264   binatorial problems. We take the same trust-boundary lesson but target probabilistic operations:
265   factor products, marginalization, normalization, posterior expectations, and decisions. BLInD [18],
266   QUITE [27], and distributional-question benchmarks [21] expose this setting from the evaluation
267   side; we turn the diagnostic into a reusable solver interface.

268   Probabilistic programming and graphical-model toolkits. Probabilistic programming systems
269   and graphical-model libraries such as ProbLog [7, 9], Stan [3], Pyro [2], Gen [6], and pgmpy [1]
270   provide mature inference machinery once a model is expressed in the required formal language.
271   Recent natural-language-to-probabilistic-program work, including LLM-BI [13] and NL-to-PLoT
272   translation [31], moves part of that specification burden to language models. VSI targets the comple-
273   mentary interface problem: the LLM assembles a typed finite-discrete route from reusable primitives,
274   deploy checks exercise it, and the accepted solver is cached rather than regenerated per query.

275   Library learning and program induction. DreamCoder [8], LILO [11], FunSearch [25],
276   PIPS [29], and agentic-skill systems [35] learn or search reusable computational structure. Here
277   the induced object is checkable: a typed TaskSpec compiles into a deterministic solver, rather than
278   arbitrary code. DisCIPL [12] and LLM-guided POMDP induction [5] also use LLMs as inductors,
279   but target text-generation control and online planning rather than exact discrete inference.

280   8   Scope and Future Work
281   Scope. VSI targets exact inference over finite discrete distributions, a broad and auditable setting
282   that covers Bayesian networks, preference learning, bandits, Naive Bayes, and HMM forward
283   filtering. The same interface can add typed atoms for continuous variables, approximate inference, or
284   distribution learning. Our evidence spans five inference families across eight datasets, plus external
285   QUITE queries and a mixed stream over supported and unsupported inputs.

286   Diagnostics and Induction. PCD is an interventional diagnostic: Compute|GoldParse intentionally
287   measures whether a model can select and execute the required probabilistic calculation once structure
288   is fixed. Its stage boundaries are coarse enough to reuse across task families, and the observed pattern
289   is stable across models, tasks, and BN depths. Family-level induction is stronger than instance-level
290   parsing; we validate it through deploy checks, template-registry held-out families, and mixed E2E
291   composition.

292   Extensibility and Verification. The operator basis is deliberately small: seven typed operations
293   plus three reusable templates. This inspectable boundary lets new families either reuse core operations,
294   as NB/HMM do, or add typed primitives behind the same validation loop. Verification is operational:
295   deploy gates execute the compiled solver and require reference agreement before registry storage.
296   Induction uses a stochastic LLM only at compile time; after validation, later inference is deterministic.

297   9   Conclusion
298   LLMs are useful probabilistic interfaces, but poor probabilistic calculators. PCD makes this failure
299   mode visible: models often recover structure and act correctly from a posterior, yet fail at the com-
300   putation itself. VSI changes the role of the LLM: the model induces a typed family specification,
301   while the compiled solver performs reusable inference. Across five inference families and external
302   QUITE queries, we measure backend exactness, natural-language robustness, and mixed routing sep-
303   arately. Within finite discrete inference, VSI is a practical compiler abstraction for LLM probabilistic
304   reasoning: language models identify reusable structure; validated solvers do the math.

442   D    23-Strategy Ablation Details
443   The 23-strategy ablation on preference learning (Flight, GPT-4o-mini) systematically varies the
444   amount of Bayesian computation offloaded from the LLM. Strategies span five categories:
445         1. No injection (baseline, random recommendation): 33–37%
446         2. Pure CoT (4 variants: reflect, Bayesian step-by-step, few-shot, self-consistency): ≤33%, at
447            or below the 3-way random baseline
448         3. Partial math injection (natural-language preferences, direct recommendation, preference +
449            recommendation): 35–39% via prompt, 42–57% via function calling
450         4. Full math injection (complete posterior weights, expected utilities, recommendation): 50%
451            via prompt, 58% via function calling
452         5. Oracle (gold posterior injected directly): 74.8%
453   The staircase is monotonic in computation offloaded: more offloading → higher accuracy. Table 6
454   provides the full numerical results.

455   Key findings. (1) Pure CoT is ineffective: all four variants score at or below the random base-
456   line, confirming that LLMs cannot improve probabilistic computation through self-reflection alone.
457   (2) Function calling consistently outperforms prompt injection for the same content. The largest
458   gain appears on mid-complexity content: direct_rec jumps from 34.8% (prompt) to 53.5% (tool),
459   a +18.7pp lift. (3) Compliance is the key mediating variable: strategies with higher compliance
460   achieve higher accuracy (r = 0.97 across all strategies). (4) Ordering matters for mixed strategies:
461   cot_then_math (49.5%) outperforms math_then_cot (40.9%) by 8.6pp, suggesting that CoT priming
462   before receiving external computation is more effective than post-hoc rationalization.

463   Content × Channel matrix. Table 7 isolates the effect of the delivery channel (prompt vs. function
464   calling) from the content delivered, forming a 2D ablation.
465   The channel gain is largest for mid-complexity content (direct recommendation: +18.7pp) and
466   smallest for content that is either useless (random: +2.8pp) or already highly informative (full math:
467   +8.4pp). This suggests that function calling primarily improves compliance, the LLM’s willingness
468   to follow the external signal, rather than adding computational ability.

471   Parse. The LLM receives the full natural-language problem and is asked to extract structured inputs
472   in a specified JSON format. For BN inference: variable names, parent–child edges, conditional
473   probability tables, query variable, and evidence assignments. For preference learning: feature names,
474   option feature vectors per round, and user choices. The extracted structure is compared field-by-field
475   against the gold parse; a sample is scored correct only if all fields match.

476   Compute|GoldParse. The LLM receives the gold structured inputs (not its own parse) and is
477   asked to perform the probabilistic computation. For BN inference: compute P (query | evidence) via
478   variable elimination. For preference learning: compute posterior-weighted expected utilities for each
479   option. BN outputs are compared against the gold probability with tolerance ϵ = 0.01. Preference
480   outputs are scored by whether the model’s self-computed utilities imply the gold recommendation.

481   Decide|GoldPosterior. The LLM receives the gold computed posterior (or expected utilities) and
482   is asked to make a decision. For BN inference: report the most likely value of the query variable. For
483   preference learning: recommend the option with the highest expected utility. The output is compared
484   against the gold decision.
485   All prompts use zero temperature where supported, max_tokens=1024–8192 depending on task com-
486   plexity, via the OpenRouter API gateway. Model identifiers: openai/gpt-4o-mini, openai/
487   gpt-4o, openai/gpt-5.4, anthropic/claude-sonnet-4, anthropic/claude-opus-4-6,
488   google/gemini-3.1-pro. All LLM calls use the OpenRouter API gateway; exact prompt tem-
489   plates, model identifiers, and runner metadata are included in the supplementary artifact.

490   F    DSL Specification

491   Types.     The DSL defines four core types:

492            • Distribution: a discrete probability distribution over a finite support set, stored as aligned
493              arrays of values and probabilities (non-negative, summing to 1).
494            • Factor: a multi-variable probabilistic factor mapping variable-assignment tuples to non-
495              negative reals. Variable domains are inferred from table keys.
496            • HypothesisSpace: defines a set of hypotheses, either as a Cartesian product of per-
497              dimension value lists or as an explicit enumeration.
498            • Evidence: a generic container for observations. Concrete subtypes include variable assign-
499              ments for BN inference, choice indices for preference learning, and arm/reward pairs for
500              bandits.

501   Core Operations (7 typed ops). Each operation is defined over the type system T =
502   {Factor, Distribution, HypothesisSpace, Evidence}. Let ϕ : Scope(ϕ) → R≥0 denote a
503   factor over variables Scope(ϕ), and e an evidence assignment.

573   M     Compile-Time Baseline Failure Analysis
574   GPT-4o and GPT-4o-mini both fail to produce working VE solvers via unconstrained code generation,
575   even with 5 rounds of self-repair. We analyze the failure modes below.

576   GPT-4o: algorithmic errors in variable elimination. GPT-4o generates code with multiple
577   algorithmic bugs: the CPT parsing regex is too greedy, failing on multi-condition entries; factor
578   construction assigns identical tuples regardless of parent values; and the sum_out function treats
579   tuple-based assignments as dictionaries, causing KeyError. Across 5 repair rounds, GPT-4o outputs
580   identical code (9,589 characters) every round, unable to diagnose its own bugs from the error
581   feedback.

582   GPT-4o-mini: data structure mismatch. GPT-4o-mini’s solver crashes with KeyError on graph
583   parsing. The generated code expects string-keyed dictionaries but receives tuple-keyed CPTs. Like
584   GPT-4o, self-repair produces nearly identical code across all 5 rounds.

585   Implications. These failures are not prompt engineering artifacts: both models receive the same 5
586   training examples and the same self-repair protocol as GPT-5.4, which succeeds after 1 repair round.
587   These failures stem from the difficulty of implementing correct VE in unconstrained Python: subtle
588   algorithmic choices in CPT representation, factor product semantics, and elimination ordering must
589   all be simultaneously correct. VSI eliminates this failure mode by constraining the inductor to a
590   declarative specification, shifting the burden of correct implementation to the deterministic compiler.
